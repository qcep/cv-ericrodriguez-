Dataflow Qwik Start - Python
GSP207

Objetivo

Ejecutar un pipeline de Apache Beam en Python usando Dataflow para contar palabras (WordCount) de un texto de Shakespeare y almacenar los resultados en Cloud Storage.

Pasos ejecutados

  1. Se configuró la región asia-southeast1 y se habilitó la API de Dataflow.
  2. Se creó un bucket de Cloud Storage (qwiklabs-gcp-02-...-bucket) para almacenar resultados y archivos temporales.
  3. Se lanzó un contenedor Docker con Python 3.12: docker run -it python:3.12 /bin/bash.
  4. Dentro del contenedor se instaló el SDK de Apache Beam: pip install apache-beam[gcp]==2.67.0.
  5. Se ejecutó el pipeline localmente con DirectRunner para validar: python -m apache_beam.examples.wordcount --output OUTPUT_FILE.
  6. Se ejecutó el pipeline en Dataflow remotamente con DataflowRunner, especificando --staging_location, --temp_location y --output en el bucket.
  7. Se verificó el job en la consola de Dataflow (estado Succeeded) y se revisaron los archivos de salida en Cloud Storage.
Concepto clave: Dataflow es el servicio gestionado de Google Cloud para ejecutar pipelines de Apache Beam. El SDK de Beam permite escribir pipelines en Python/Java que se ejecutan localmente (DirectRunner) o en la nube (DataflowRunner). El parámetro temp_location debe ser una URL válida de Cloud Storage (gs://...).
Resultado: Job wordcount ejecutado exitosamente. Se generaron archivos output-00000-of-00001 en gs://bucket/results/ con el conteo de palabras del texto de Shakespeare.

Validate Data Quality for a Batch Data Pipeline using Serverless for Apache Spark
Intermediate

Objetivo

Construir un pipeline batch con PySpark (Serverless Spark) que valide la calidad de datos de un CSV de clientes, separe registros válidos (a BigQuery) e inválidos (a una DLQ en Cloud Storage).

Pasos ejecutados

  1. Se exploró el entorno provisionado por Terraform: VPC, subnet, buckets (main y DLQ), y archivo CSV de 1000 registros con ~20% de datos inválidos (IDs nulos, emails malformados).
  2. Se creó un dataset en BigQuery llamado customer_data_clean para almacenar los datos limpios.
  3. Se escribió un script PySpark (customer_dq.py) que: lee el CSV desde GCS, aplica reglas de calidad (ID no nulo y email con formato válido usando regex), separa el DataFrame en clean_df y error_df, escribe los limpios en BigQuery y los inválidos en la DLQ (GCS).
  4. Se subió el script a Cloud Storage y se ejecutó un batch job con gcloud dataproc batches submit pyspark, especificando la subnet, región, bucket de dependencias y el script.
  5. Se verificó en BigQuery que la tabla valid_customers tenía ~798 registros limpios.
  6. Se revisó la DLQ en GCS para confirmar que los ~200 registros inválidos se guardaron correctamente.
Concepto clave: Serverless Spark en Dataproc permite ejecutar jobs de Spark sin gestionar un clúster. La validación de calidad de datos (DQ) es fundamental en pipelines ETL: se aplican reglas (ej. regex para emails, campos no nulos) y se separan los registros que no cumplen para su análisis posterior en una Dead Letter Queue (DLQ).
Resultado: Batch job customer-dq-job exitoso. ~800 registros limpios en BigQuery (customer_data_clean.valid_customers) y ~200 registros inválidos en gs://...-dlq-bucket/errors/.

Building Batch Pipelines in Cloud Data Fusion

Objetivo

Usar Cloud Data Fusion (CDF) para construir un pipeline ETL visual que cargue un CSV (titanic.csv) desde GCS, lo transforme con Wrangler y lo escriba en BigQuery.

Pasos ejecutados

  1. Se creó un bucket y se subió titanic.csv (893 registros) desde un bucket público de Google.
  2. Se otorgaron permisos IAM a la instancia de CDF: roles Cloud Data Fusion API Service Agent, Dataproc Administrator y Service Account User.
  3. Se abrió la UI de CDF y se usó Wrangler para transformar el CSV: directiva parse-as-csv :body ',' true para parsear el CSV y drop :body para eliminar la columna raw.
  4. Se creó un pipeline batch en Pipeline Studio con 3 nodos: GCSFile (source) → Wrangler (transform) → BigQuery (sink).
  5. Se configuraron las propiedades del nodo BigQuery: dataset demo, tabla titanic.
  6. Se guardó y desplegó el pipeline (ETL-batch-pipeline), se ejecutó y se verificó que 892 registros se cargaron en demo.titanic.
Concepto clave: Cloud Data Fusion es una plataforma visual de integración de datos basada en CDAP. Wrangler permite transformar datos de forma interactiva con directivas (como parse-as-csv y drop). Pipeline Studio permite diseñar pipelines ETL arrastrando y soltando nodos (source, transform, sink).
Resultado: Pipeline ETL ejecutado con éxito. 892 registros del Titanic cargados en BigQuery (demo.titanic).

ETL Processing on Google Cloud Using Dataflow and BigQuery (Python)
GSP290

Objetivo

Ejecutar 4 pipelines ETL con Apache Beam en Python: ingesta, transformación, enriquecimiento y join (data lake a data mart), usando Dataflow y BigQuery.

Pasos ejecutados

  1. Se re-habilitó la API de Dataflow.
  2. Se descargó el repositorio de código dataflow-python-examples desde GCS.
  3. Se creó un bucket, se copiaron los archivos usa_names.csv y head_usa_names.csv, y se creó el dataset lake en BigQuery.
  4. Se lanzó un contenedor Docker con Python 3.8 y se instaló apache-beam[gcp]==2.59.0.
  5. Pipeline 1 - Ingesta: data_ingestion.py leyó el CSV de GCS, filtró el header y escribió en lake.usa_names.
  6. Pipeline 2 - Transformación: data_transformation.py transformó el año a tipo DATE y escribió en lake.usa_names_transformed.
  7. Pipeline 3 - Enriquecimiento: data_enrichment.py aplicó lógica custom (se editó la línea 83 para usar x en lugar de x.decode("utf8")) y escribió en lake.usa_names_enriched.
  8. Pipeline 4 - Join: data_lake_to_mart.py leyó dos tablas de BigQuery (lake.orders y lake.customers), hizo un join con side input y escribió en lake.orders_denormalized_sideinput.
Concepto clave: ETL (Extract, Transform, Load) es el patrón clásico de integración de datos. Apache Beam permite escribir pipelines que se ejecutan en Dataflow. Los side inputs permiten hacer joins en pipelines de streaming/batch. Cada pipeline es independiente y escribe en una tabla diferente del dataset lake.
Resultado: 4 pipelines ejecutados exitosamente. Tablas creadas en lake: usa_names, usa_names_transformed, usa_names_enriched, orders_denormalized_sideinput.

Objetivo

Construir un pipeline de streaming en CDF que lea mensajes de Pub/Sub (tweets JSON), los transforme con Wrangler y los escriba en BigQuery en tiempo real.

Pasos ejecutados

  1. Se verificaron permisos del proyecto y se re-habilitó la API de Dataflow.
  2. Se creó un bucket y se subió un archivo de tweets JSON (pubnub_tweets_2019-06-09).
  3. Se creó un topic de Pub/Sub (cdf_lab_topic) y una subscription (cdf_lab_subscription).
  4. Se otorgaron permisos IAM: CDF API Service Agent, Managed Service for Spark Administrator y Service Account User.
  5. Se abrió la UI de CDF y se creó un pipeline realtime.
  6. Se usó Wrangler para aplicar 19 directivas, incluyendo: parse-as-json :body 1 (parsear JSON), parse-as-simple-date :created_at EEE MMM dd HH:mm:ss Z yyyy (parsear fecha de Twitter), drop de columnas irrelevantes, set-type :possibly_sensitive boolean.
  7. Se añadieron directivas al top: keep :message, set-charset :message 'utf-8', rename :message :body (para compatibilidad entre Pub/Sub y Wrangler).
  8. Se configuró el pipeline: PubSub (source) → Wrangler (transform) → BigQuery (sink, tabla realtime.tweets).
  9. Se desplegó y ejecutó el pipeline en modo streaming.
  10. Se lanzó un job de Dataflow con la plantilla Text Files on Cloud Storage to Pub/Sub para enviar los tweets del archivo al topic.
  11. Se verificaron las métricas: ~500 eventos procesados de Pub/Sub a BigQuery.
Concepto clave: Los pipelines realtime en CDF se ejecutan en un clúster de Spark Streaming. A diferencia de los batch, no terminan: quedan corriendo continuamente procesando eventos. La integración con Pub/Sub permite ingestar datos en tiempo real. Wrangler puede parsear JSON anidado con parse-as-json.
Resultado: Pipeline Realtime_Pipeline corriendo. Eventos de tweets fluyendo de Pub/Sub a BigQuery (realtime.tweets) en tiempo real. ~500 eventos procesados.

Construir un pipeline de Dataflow que enriquece datos de compras de DLC de esports usando Bigtable, aplica un modelo de PyTorch para generar recomendaciones y emite los resultados.

Pasos ejecutados

  1. Se crearon recursos: instancia de Bigtable (instance con cluster my-cluster), topic de Pub/Sub (customer-data) y subscription (customer-data_sub).
  2. Se abrió un notebook de Workbench (JupyterLab) con kernel Python 3.
  3. Se instalaron paquetes: pip install torch apache-beam[gcp].
  4. Se configuraron variables: PROJECT_ID, INSTANCE_ID, TABLE_ID.
  5. Se entrenó un modelo PyTorch (DLCRecommender) con 10 epochs, logrando una accuracy del 94.2%.
  6. Se creó una tabla en Bigtable (customer_data) con 3 column families: customer_info, purchase_history, demographics. Se insertaron 5 filas de ejemplo.
  7. Se publicaron mensajes de compra a Pub/Sub.
  8. Se configuró un BigtableEnrichmentHandler para enriquecer los mensajes de Pub/Sub con datos de Bigtable usando player_id como row key.
  9. Se configuró un PyTorchModelHandlerTensor para cargar el modelo entrenado y hacer inferencia.
  10. Se construyó el pipeline: Pub/Sub → Bigtable Enrichment → PyTorch Inference → Top-3 Recommendations.

Concepto clave: Bigtable es una base de datos NoSQL de baja latencia ideal para enriquecimiento en tiempo real. Apache Beam permite integrar modelos de ML (PyTorch) en pipelines de datos usando RunInference. El enriquecimiento combina datos de streaming (Pub/Sub) con datos de referencia (Bigtable) para generar recomendaciones personalizadas.
Resultado: Pipeline ejecutado. Modelo PyTorch entrenado (94.2% accuracy). Recomendaciones top-3 generadas para player_4521. Pipeline: Pub/Sub → Bigtable → PyTorch → Recomendaciones.

Stream Processing with Pub/Sub and Dataflow: Qwik Start
GSP903

Objetivo

Construir un pipeline de streaming con Apache Beam (Java o Python) que lea mensajes de Pub/Sub, los agrupe en ventanas de tiempo fijo (FixedWindows de 2 minutos) y escriba un archivo por ventana en Cloud Storage.

Pasos ejecutados

  1. Se configuró la región us-central1 y se habilitó la API de Dataflow.
  2. Se crearon variables: PROJECT_ID, BUCKET_NAME, TOPIC_ID=my-id.
  3. Se creó un bucket, un topic de Pub/Sub (my-id), una app de App Engine y un job de Cloud Scheduler (publisher-job) que publica "Hello!" cada minuto.
  4. Se clonó el repositorio java-docs-samples y se revisó el código PubSubToGcs.java.
  5. El pipeline: PubsubIO.readStrings().fromTopic() → Window.into(FixedWindows.of(Duration.standardMinutes(2))) → WriteOneFilePerWindow.
  6. Se compiló y ejecutó el pipeline con Maven y DataflowRunner, especificando --windowSize=2.
  7. Se observó el job en Dataflow: workers iniciados, pipeline corriendo, ventanas de 2 minutos disparando.
  8. Se verificaron los archivos en GCS: output-{HH:MM}-{HH:MM}-0-of-1 (un archivo por ventana).
  9. Se realizó el cleanup: eliminar Scheduler job, detener Dataflow job, eliminar topic, archivos y bucket.
Concepto clave: Las ventanas (windows) en Beam permiten agrupar datos de streaming en intervalos de tiempo. FixedWindows divide el stream en ventanas de tamaño fijo (ej. 2 minutos). WriteOneFilePerWindow es un sink que escribe un archivo por cada ventana. Cloud Scheduler permite generar tráfico periódico a Pub/Sub.
Resultado: Pipeline pubsubtogcs ejecutado. Archivos de salida en gs://bucket/samples/output-* (4 archivos de ~2 KiB cada uno). Cleanup completo de recursos.

Desplegar un cluster de Apache Kafka en una VM de Compute Engine, crear topics, producir mensajes, ejecutar una aplicación de Kafka Streams (WordCount) y consumir los resultados.

  1. Se creó una regla de firewall (allow-iap-ssh) para permitir SSH a través de Identity-Aware Proxy.
  2. Se desplegó una VM (kafka-1-vm, e2-medium) desde Marketplace con Apache Kafka Server on Ubuntu 24.04.
  3. Se añadió el tag iap-gce a la VM para permitir SSH.
  4. Se accedió por SSH a la VM y se arrancó Kafka: cd /opt/kafka/, bin/kafka-storage.sh format, bin/kafka-server-start.sh config/server.properties.

Setup IAM and Networking for your Dataflow Jobs
GSP1134

Objetivo

Configurar roles IAM y redes (Private Google Access) para ejecutar jobs de Dataflow con IPs privadas, entendiendo los errores de permisos y conectividad.

Pasos ejecutados

  1. Se creó un bucket en Cloud Storage (gs://PROJECT_ID) para staging del job.
  2. Se verificó el IAM policy del proyecto: el usuario solo tenía rol Editor, sin dataflow.admin.
  3. Intento 1 (fallido): Se lanzó el job job1 (Word_Count). Falló con PERMISSION_DENIED: dataflow.jobs.create.
  4. Se asignó el rol roles/dataflow.admin al usuario.
  5. Retry exitoso: Se lanzó job1 de nuevo. Job completado en ~5 min. WordCount de King Lear ejecutado.
  6. Intento 2 (fallido): Se lanzó job2 con --disable-public-ips. Falló porque los workers no podían acceder a APIs de GCS/Dataflow sin IPs públicas (Private Google Access deshabilitado).
  7. Se asignó el rol roles/compute.networkAdmin al usuario.
  8. Se habilitó Private Google Access en la subnet default: gcloud compute networks subnets update default --region=us-central1 --enable-private-ip-google-access.
  9. Retry exitoso: Se lanzó job2 de nuevo con --disable-public-ips. Job completado. VMs lanzadas sin IP externa y eliminadas al terminar.
Concepto clave: Private Google Access (PGA) permite que las VMs sin IP pública accedan a las APIs de Google (GCS, BigQuery, etc.) a través de la red interna de Google. Sin PGA, las VMs con --disable-public-ips no pueden comunicarse con los servicios de Google. Los roles IAM (dataflow.admin, compute.networkAdmin) son necesarios para crear jobs y modificar configuraciones de red.
Resultado: job1 exitoso tras asignar dataflow.admin. job2 exitoso tras habilitar PGA y asignar compute.networkAdmin. VMs sin IP pública funcionando correctamente.
