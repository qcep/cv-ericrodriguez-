Contexto

Escenario: QuickCommerce

Eres Data Engineer en QuickCommerce, una plataforma e-commerce que procesa 50,000 órdenes por hora en pico. El equipo de BI necesita tracking de ingresos en tiempo real, pero actualmente los datos solo están disponibles 12 horas después vía ETL batch nocturno.

Nota sobre co-partitioning

Los topics orders y payments deben tener el mismo número de particiones (8) y usar la misma key (order_id) para que los eventos relacionados aterricen en la misma partición.

Actividad 1

Setup del Entorno Kafka

Iniciar un clúster Kafka local de 3 brokers con Docker Compose y crear los tres topics con los counts de particiones correctos.

Paso 1: Iniciar el Clúster

docker-compose up -d
docker ps # verificar 3 brokers healthy

Paso 2: Crear Topic "orders"

8 particiones, keyed por order_id, replication factor 3 (cluster de 3 brokers).

kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic orders \
  --partitions 8 \
  --replication-factor 3 \
  --config cleanup.policy=delete

Paso 3: Crear Topic "payments" (Co-partitioned)

Mismo número de particiones (8) para habilitar el join distribuido.

kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic payments \
  --partitions 8 \
  --replication-factor 3 \
  --config cleanup.policy=delete

Paso 4: Crear Topic de Salida

kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic category-revenue \
  --partitions 4 \
  --replication-factor 3

Verificar todos los topics:

kafka-topics.sh --bootstrap-server localhost:9092 --list
Output esperado

category-revenue, orders, payments — los tres con los counts de particiones correctos.

Regla crítica de co-partitioning

Ambos topics deben tener 8 particiones y usar order_id como key. Si no cumplen esto, el join fallará silenciosamente: eventos relacionados serán procesados por instancias distintas y nunca se encontrarán.

Actividad 2

Implementar el Stream-Stream Join

Definir los modelos de datos, crear el esqueleto de la aplicación Kafka Streams e implementar el join entre orders y payments con una ventana de 5 minutos.

Modelos de Datos

Order.java

public class Order {
  private String orderId;
  private String categoryId;
  private String customerId;
  private long timestamp;

  // getters, setters, constructors, empty constructor
}

Payment.java

public class Payment {
  private String orderId;
  private double paymentAmount;
  private String paymentMethod;
  private long timestamp;

  // getters, setters, constructors
}

OrderPayment.java (resultado del join)

public class OrderPayment {
  private String orderId;
  private String categoryId;
  private String customerId;
  private double paymentAmount;
  private String paymentMethod;
  private long orderTimestamp;
  private long paymentTimestamp;
}

Implementación del Join

// 1. Leer streams desde los topics
KStream<String, Order> orders = builder.stream("orders",
  Consumed.with(Serdes.String(), orderSerde));

KStream<String, Payment> payments = builder.stream("payments",
  Consumed.with(Serdes.String(), paymentSerde));

// 2. Asegurar que ambos streams estén keyed por order_id
// (las keys ya deben venir correctamente desde los producers)

// 3. Realizar el join con ventana de 5 minutos
KStream<String, OrderPayment> joined = orders.join(
  payments,
  // ValueJoiner: combina Order + Payment
  (order, payment) -> new OrderPayment(
    order.getOrderId(),
    order.getCategoryId(),
    order.getCustomerId(),
    payment.getPaymentAmount(),
    payment.getPaymentMethod(),
    order.getTimestamp(),
    payment.getTimestamp()
  ),
  // Join window de 5 minutos (sin grace period)
  JoinWindows.ofTimeDifferenceWithNoGrace(
    Duration.ofMinutes(5)),
  Joined.with(Serdes.String(), orderSerde, paymentSerde)
);
¿Por qué 5 minutos?

El gateway de pago puede tardar entre 30 segundos y 2 minutos. La ventana de 5 minutos cubre ese rango con margen, capturando ~99.7% de los matches (como aprendimos del caso Food Delivery).

Serdes Personalizados

public class JsonSerde<T> extends Serde {
  private final ObjectMapper mapper = new ObjectMapper();
  private final Class<T> type;

  public JsonSerde(Class<T> type) { this.type = type; }

  @Override
  public void configure(Map<String, ?> configs, boolean isKey) {}

  @Override
  public void close() {}

  @Override
  public Serializer<T> serializer() {
    return (topic, data) -> {
      try { return data == null ? null : mapper.writeValueAsBytes(data); }
      catch (Exception e) { throw new SerializationException(e); }
    };
  }

  @Override
  public Deserializer<T> deserializer() {
    return (topic, data) -> {
      try { return data == null ? null : mapper.readValue(data, type); }
      catch (Exception e) { throw new SerializationException(e); }
    };
  }
}
Output esperado

Un KStream<String, OrderPayment> donde la key es order_id y el value combina los campos de Order y Payment.

Actividad 3

Agregación por Ventana Tumbling

Re-keyear el stream por category_id, aplicar ventanas tumbling de 5 minutos y agregar los ingresos totales y el conteo de órdenes por categoría.

Flujo de la Agregación

KStream Join key: order_id
groupBy key: category_id
windowedBy TimeWindows(5m)
aggregate CategoryRevenue

Implementación

CategoryRevenue.java

public class CategoryRevenue {
  private String categoryId;
  private long windowStart;
  private long windowEnd;
  private double totalRevenue;
  private long orderCount;
}

Topología de Agregación

// 1. Rekeyear por category_id (trigger repartition)
KGroupedStream<String, OrderPayment> grouped = joined
  .groupBy(
    (orderId, op) -> op.getCategoryId(),
    Grouped.with(Serdes.String(), orderPaymentSerde)
  );

// 2. Aplicar ventanas tumbling de 5 minutos
TimeWindowedKStream<String, OrderPayment> windowed = grouped
  .windowedBy(
    TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5))
  );

// 3. Agregar: sum(payment_amount) + count(orders)
KTable<Windowed<String>, CategoryRevenue> revenue = windowed
  .aggregate(
    // Initializer
    () -> new CategoryRevenue(null, 0, 0, 0.0, 0),
    // Adder
    (category, op, agg) -> {
      agg.setCategoryId(category);
      agg.setTotalRevenue(agg.getTotalRevenue() + op.getPaymentAmount());
      agg.setOrderCount(agg.getOrderCount() + 1);
      return agg;
    },
    // Materialize con nombre de state store
    Materialized.<String, CategoryRevenue, WindowStore<Bytes, byte[]>>
      as("category-revenue-store")
      .withKeySerde(Serdes.String())
      .withValueSerde(categoryRevenueSerde)
  );

// 4. Convertir a KStream y escribir al topic
revenue.toStream()
  .map((windowedKey, value) -> {
    value.setWindowStart(windowedKey.window().start());
    value.setWindowEnd(windowedKey.window().end());
    return KeyValue.pair(value.getCategoryId(), value);
  })
  .to("category-revenue",
    Produced.with(Serdes.String(), categoryRevenueSerde));
Repartition Esperado

El groupBy() cambia la key de order_id a category_id, lo que dispara un repartition interno. Esto es necesario y esperado: Kafka Streams crea un topic interno de repartición para redistribuir los eventos por la nueva key.

05
Garantía

Exactly-Once Semantics (EOS)

Configurar processing.guarantee=exactly_once_v2 para garantizar que no haya doble conteo de ingresos, incluso ante fallos o reinicios.

Configuración

# application.properties
application.id=quickcommerce-revenue
bootstrap.servers=localhost:9092
default.key.serde=org.apache.kafka.common.serialization.Serdes$StringSerde
default.value.serde=com.example.JsonSerde

# EXACTLY-ONCE SEMANTICS v2
processing.guarantee=exactly_once_v2

# Optimizaciones
commit.interval.ms=100
cache.max.bytes.buffering=10485760
num.stream.threads=4

¿Qué hace exactly_once_v2?

Idempotent Producer
✓
Sin duplicados en retry
Transactional Writes
✓
Atomicidad de output + state
Read-Committed
✓
Consumidores ven solo commits
EOS v2 vs v1

v2 (Kafka 3.0+) es más eficiente: no requiere un topic de transacciones por tarea, y funciona nativamente con brokers en KRaft mode. Es el estándar para nuevas aplicaciones.

Garantías Resultantes

Sin EOS (at-least-once)

  • Posibles duplicados en retry
  • Revenue inflado tras fallos
  • Inconsistencia entre state y output
  • Requiere deduplicación downstream

Con EOS v2

  • Sin duplicados (idempotent producer)
  • Revenue exacto siempre
  • Atomicidad state + output
  • Consumidores leen solo commits

Paso 4: Verificar Exactly-Once

Procedimiento para validar EOS:

1. Iniciar la aplicación

Ejecutar el job Kafka Streams y comenzar a procesar eventos.

2. Matar el proceso mid-processing

Enviar Ctrl+C o kill -9 mientras hay eventos en tránsito.

3. Reiniciar la aplicación

Volver a lanzar el job. Kafka Streams restaurará el state store y reanudará desde el último offset commiteado.

4. Verificar output

Consumir con --from-beginning y confirmar que no hay duplicados: los totales permanecen idénticos.

Criterio de éxito

Después del reinicio, los ingresos totales por categoría deben ser exactamente los mismos que antes del fallo. Si hubiera duplicados, veríamos revenue inflado (ej: $449.49 × 2 = $898.98).

Síntesis

Resumen y Entregables

Los patrones implementados son los mismos que usan DoorDash, Robinhood y Netflix para analytics en tiempo real a escala.

Conceptos Clave Aplicados

1. Co-partitioning de topics

Ambos topics con 8 particiones y misma key (order_id) para que el join distribuido funcione.

2. Stream-Stream join con ventana

JoinWindows.ofTimeDifferenceWithNoGrace(Duration.ofMinutes(5)) cubre delays de pago de hasta 2 min.

3. Repartition por cambio de key

groupBy(category_id) dispara repartition interno, necesario para agregar correctamente en distributed.

4. Tumbling windows

Ventanas de 5 minutos no solapadas, con TimeWindows.ofSizeWithNoGrace.

5. Exactly-once semantics

processing.guarantee=exactly_once_v2 previene doble conteo de revenue ante fallos.
