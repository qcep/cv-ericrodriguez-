ShopLive: El Dashboard de Campaña

Executives necesitan un dashboard live durante una campaña de alto tráfico. El objetivo es publicar un KPI de orders per minute (OPM) y asegurar recuperación si el stream se interrumpe.

Objetivos del Lab

  • Conectar la streaming KPI table a Databricks AI/BI Dashboards (o Apache Superset).
  • Configurar una refresh strategy (ej: 60-second auto-refresh o view limitada a últimos 60 min).

  • Verificar que los tiles del dashboard retornan valores correctos al resumir el stream.
  • Inspeccionar query progress para entender throughput, latency y freshness trade-offs.

Challenge 2: KPI Aggregation

from pyspark.sql.functions import window, col, count as f_count

kpi_df = (orders_df
  .withWatermark("event_time", "10 minutes")
  .groupBy(window(col("event_time"), "1 minute"))
  .agg(f_count("*").alias("orders_per_minute"))
)
orders_df event_time
withWatermark 10 min
window(1 min) tumbling
kpi_df window, orders_per_minute
Watermark vs Window

Watermark (10 min) > Window (1 min). Esto permite que las ventanas finalicen correctamente después de aceptar eventos ligeramente tardíos.

Challenge 3: Failure-aware Delta Sink

Simula una interrupción antes de escribir a Delta usando foreachBatch:

# 4) Failure-aware streaming sink
SIMULATE_FAILURE = True # toggle a False para recovery

def write_batch(batch_df, batch_id):
  print(f"[write_batch] batch_id={batch_id}, rows={batch_df.count()}")
  if SIMULATE_FAILURE:
    raise Exception("Simulated interruption before Delta write")
  (batch_df.write
    .format("delta")
    .mode("append")
    .save(delta_kpi_path))

q_kpi = (kpi_df.writeStream
  .foreachBatch(write_batch)
  .option("checkpointLocation", f"{checkpoint_root}/kpi")
  .trigger(availableNow=True)
  .start())
Simulación de fallo

Con SIMULATE_FAILURE=True, el job lanza excepción antes de escribir. El checkpoint registra que el batch falló, y en el siguiente run se reintenta desde el mismo offset.

Activity 5

Recovery: Simulación y Restart

Blackouts happen. Debemos probar recovery correcto reutilizando el mismo checkpoint y generando nuevos archivos.

Procedimiento de Recovery

1. Detener el job (o lanzar excepción)

Con SIMULATE_FAILURE=True, el primer run falla antes de escribir.

2. Generar nuevos archivos

Ejecutar generate_orders_wave() para simular nuevo tráfico entrante.

3. Re-ejecutar con mismo checkpoint

Cambiar SIMULATE_FAILURE=False y re-lanzar el job. Spark retoma desde el offset fallido.

4. Verificar no duplicados

Delta no debe duplicar filas de runs anteriores. Checkpoint tracks offsets + state + commit logs.

Exactly-once semantics

El checkpoint permite que Spark retome desde el último offset commiteado. numInputRows refleja solo nuevos datos. Delta no duplica filas previas.

Verification Output

Last progress (post-recovery) numInputRows: 0 inputRowsPerSecond: 0.0 processedRowsPerSecond: 0.0 batchDuration: 1ms # Delta no duplica filas SELECT COUNT(*) FROM vw_kpi_orders_minute_all; → 8 (sin cambios)

Activity 4

SQL Views para Dashboards

Los dashboards deben queryar stable views con friendly time windows, no tablas completas.

Registro de View (last60)

# Crear UC VIEWS sobre el Delta path (works on Free)
spark.sql(f"""
CREATE OR REPLACE VIEW {CATALOG}.{SCHEMA}.vw_kpi_orders_minute_all AS
SELECT *
FROM delta.`{delta_kpi_path}`
""")

spark.sql(f"""
CREATE OR REPLACE VIEW {CATALOG}.{SCHEMA}.vw_kpi_orders_minute_last60 AS
SELECT
  CAST(`window`.start AS TIMESTAMP) AS minute_start,
  orders_per_minute
FROM {CATALOG}.{SCHEMA}.vw_kpi_orders_minute_all
WHERE `window`.start >= current_timestamp() - INTERVAL 60 MINUTES
""")
Time-bounded views

Limitar a los últimos 60 minutos mejora latencia y reduce BI compute. Charts cargan solo los puntos que necesitan.

Dashboard Connection

Databricks AI/BI

  1. SQL → Dashboards → New dashboard → Add tile (SQL).
  2. Query: SELECT minute_start, orders_per_minute FROM vw_kpi_orders_minute_last60 ORDER BY minute_start DESC LIMIT 60.
  3. Line/bar chart + Auto-refresh ≈ 60s.

Apache Superset

  1. Connect to Databricks SQL Warehouse via JDBC.
  2. Create dataset based on the view.
  3. Build chart + auto-refresh 60-120s.
Refresh strategy

60s balancea freshness y cost. Refrescar más rápido que el window size (1 min) no da beneficios visibles, solo quema compute.

Common Issues & Solutions

Problema Causa Solución
Nothing on dashboard Sin archivos antes de availableNow Ejecutar simulador primero
Duplicates after re-run Checkpoint cambiado Confirmar mismo checkpoint
Permission/registration error Sin UC privileges Usar Volume existente o pedir admin
Null spikes on tile View filtra incorrecto Asegurar view filtra ventana correcta
Delta not found Sink nunca corrió Ejecutar Delta sink al menos una vez

Principios Clave

1. Correctness y continuity importan tanto como freshness

Un dashboard que muestra números incorrectos es peor que uno que no actualiza.

2. availableNow + checkpoint = idempotencia

Re-runs con mismo checkpoint no duplican output.

3. Views bounded mejoran latencia

Query solo los últimos 60 min, no toda la historia.

4. Monitor query progress continuamente

Detecta bottlenecks antes de que impacten el dashboard.
