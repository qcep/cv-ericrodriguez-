01
Contexto

FinPulse: La Métrica de Usuarios Activos

El liderazgo de FinPulse requiere una métrica confiable de dashboards: usuarios activos únicos cada 15 minutos, desglosados por región. Este proyecto construye esa métrica con garantías de event-time correctness.

Objetivos del Proyecto

  • Conectar a Kafka para un stream real.
  • Parsear eventos en columnas tipadas con schema explícito.
  • Computar una ventana tumbling de 15 minutos por región para contar usuarios únicos.
  • Aplicar un watermark para incluir eventos ligeramente tardíos y descartar los muy tardíos de forma segura.
  • Escribir resultados a Delta Lake con checkpointing para confiabilidad y continuidad.

Esquema de Datos

Campo Tipo Descripción
user_id string Identificador del usuario (ej: U-00001)
event_time timestamp Cuándo ocurrió el evento (business time)
region string NA, EU, APAC, LATAM
action string login, view, purchase

Topología del Pipeline

Kafka / File events_df
withWatermark 20 minutes
window(15 min) groupBy region
approx_count_distinct unique_users
Delta delta_active_users
Dual source

El notebook soporta Kafka real (format("kafka") → cast value → from_json) o file simulator (readStream.json con schema y badRecordsPath). El flag USE_FILE_SIM controla cuál se usa.

Generador de Eventos (Fallback)

Simula actividad de usuarios con late_ratio para probar watermarks:

import json, time, uuid, random
from datetime import datetime, timedelta

regions = ["NA","EU","APAC","LATAM"]
actions = ["login","view","purchase"]

def generate_user_activity_wave(n_files=2, rows_per_file=80, late_ratio=0.2):
  for _ in range(n_files):
    path = f"{inbox_path}/batch_{int(time.time())}_{uuid.uuid4().hex}.json"
    lines = []
    for r in range(rows_per_file):
      now = datetime.utcnow()
      if random.random() < late_ratio:
        et = now - timedelta(minutes=random.randint(1,10))
      else:
        et = now
      evt = {
        "user_id": f"U-{random.randint(1, 5000):05d}",
        "event_time": et.strftime("%Y-%m-%dT%H:%M:%S.%fZ"),
        "region": random.choice(regions),
        "action": random.choice(actions)
      }
      lines.append(json.dumps(evt))
    dbutils.fs.put(path, "\n".join(lines), overwrite=True)

Challenge 2: Streaming Source

Path Kafka

raw = (spark.readStream

Activity 3

15-min Windows + Watermark + Unique Users

La combinación de tumbling window de 15 minutos con watermark de 20 minutos garantiza que las métricas de usuarios activos sean event-time accurate y bounded en estado.

Challenge 3: Aggregation

agg_df = (events_df
  .withWatermark("event_time", "20 minutes")
  .groupBy(
    window(col("event_time"), "15 minutes"),
    col("region")
  )
  .agg(approx_count_distinct("user_id").alias("unique_users"))
)
events_df event_time
withWatermark 20 min
window(15 min) tumbling
groupBy region + approx_count_distinct
agg_df window, region, unique_users

Decisiones Técnicas

¿Por qué 15 minutos?

  • Granularidad suficiente para detectar tendencias sin ruido excesivo.
  • Balance entre frescura y costo de cómputo.
  • Compatible con dashboards ejecutivos.

¿Por qué watermark de 20 minutos?

  • Mayor que la ventana (15 min): permite finalizar ventanas correctamente.
  • Captura eventos tardíos: el generador simula hasta 10 min de latencia.
  • Bounded state: descarta eventos más viejos sin crecer indefinidamente.

¿Por qué approx_count_distinct?

  • Streaming-friendly: no requiere mantener todos los user_ids en memoria.
  • Eficiente: usa HyperLogLog con error ~2%.
  • Suficiente para BI: dashboards no necesitan exactitud perfecta en unique counts.
Watermark < ventana = problema

Si el watermark fuera menor que la ventana (ej: 10 min con ventana de 15 min), las ventanas podrían finalizar antes de recibir todos los eventos, perdiendo datos válidos.

Activities 4-5

Sinks: Console y Delta

Dos sinks con outputMode("append") y checkpoints independientes. Console para preview, Delta para serving layer del dashboard.

Challenge 4: Console Sink

q_console = (agg_df.writeStream
  .format("console")
  .outputMode("append")
  .option("truncate", "false")
  .option("numRows", 100)
  .option("checkpointLocation", f"{checkpoint_root}/console")
  .trigger(availableNow=True)
  .start())
q_console.awaitTermination()

Challenge 5: Delta Sink

q_delta = (agg_df.writeStream
  .format("delta")
  .outputMode("append")
  .option("checkpointLocation", f"{checkpoint_root}/delta")
  .trigger(availableNow=True)
  .start(delta_out_path))
q_delta.awaitTermination()
Append mode + watermark = ventanas finalizadas

Con append mode, Spark solo emite ventanas que han pasado el watermark. Cada ventana se emite una vez y nunca se actualiza — exactamente lo que BI necesita.

Troubleshooting

Validación y Problemas Comunes

Checklist de éxito y soluciones a issues frecuentes en Databricks Free Edition.

Success Checklist

  • Volume creado/validado y carpetas bajo <volume>/finpulse.
  • Streaming source construido (Kafka o file) con schema explícito.
  • 15-min event-time window + watermark aplicados.
  • Aggregates persistidos a Delta con checkpointing.
  • Re-runs con availableNow procesan nuevas waves sin duplicados.

Common Issues & Solutions

Problema Causa Solución
Delta read error (_delta_log missing) Delta sink no ha corrido aún Ejecutar el Delta sink al menos una vez (usar la celda de safe validation)
No console output Sin archivos/mensajes antes de availableNow Generar archivos (o producir Kafka messages) primero
Permission error creating Volume Sin privilegios UC Pedir a un admin, o usar un Volume existente
Duplicates Checkpoint paths cambiados Mantener checkpoint paths estables entre runs

Principios Clave

1. Event time es la verdad del negocio

Window sobre event_time, no sobre cuándo Spark vio el evento.

2. Watermark > ventana

20 min de watermark para 15 min de ventana permite capturar latencia y finalizar correctamente.

3. approx_count_distinct para unique counts

Streaming-friendly, eficiente, error ~2% aceptable para BI.

4. availableNow + checkpoints

Combinación clave para idempotencia en Databricks Free.

5. Correctness + reliability son no negociables

Dashboards ejecutivos requieren métricas estables, no solo rápidas.
