01
Setup

Configuración del Entorno

Iniciar el clúster de Kafka con un solo broker y crear el tópico payment-transactions con una retención de 14 días (la configuración "incorrecta" que necesitamos corregir).

Iniciar el Laboratorio

Ejecutar el script de setup desde la carpeta del módulo:

cd module1-demo
./setup.sh

Esto realizará las siguientes acciones:

  • Iniciar un contenedor Docker con Apache Kafka 3.7.0.
  • Esperar a que el broker esté saludable.
  • Crear el tópico payment-transactions con 8 particiones, factor de replicación 1 y retención de 14 días (1209600000 ms).
Nota

El script está diseñado para ser ejecutado una y otra vez, eliminando el tópico si ya existe para asegurar un estado limpio en cada demostración.

02
Ejercicio 1

Descubrir la Configuración Actual

Ingresar al contenedor de Kafka y usar kafka-configs.sh para inspeccionar la retención actual del tópico.

Inspeccionar el Tópico

Primero, ingresar al contenedor:

docker exec -it kafka-demo bash

Luego, ejecutar el comando de descripción:

/opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics \
  --entity-name payment-transactions \
  --describe

¿Qué buscar?

  • El valor de retention.ms.
  • Convertirlo a días: 1209600000 ms ÷ 86400000 ms/día = ?
Resultado

La retención es de 14 días (1,209,600,000 ms ÷ 86,400,000 ms/día = 14 días). PCI-DSS requiere 30 días, por lo que estamos 16 días por debajo del cumplimiento.

04
Ejercicio 3

Aplicar la Solución

Modificar la retención del tópico a 30 días (2,592,000,000 ms) y verificar el cambio.

Actualizar Retención

Dentro del contenedor, ejecutar:

/opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics \
  --entity-name payment-transactions \
  --alter \
  --add-config retention.ms=2592000000

Verificar el cambio:

/opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics \
  --entity-name payment-transactions \
  --describe

Preguntas de reflexión

  • ¿Fue necesario reiniciar Kafka para aplicar el cambio?
  • ¿Qué sucede con los datos existentes al aumentar la retención?
Respuestas

1. No se requiere reinicio. Kafka aplica los cambios de configuración de forma dinámica.

2. Los datos existentes se preservan. La nueva retención solo afecta el momento en que los datos expiran, no los mensajes ya almacenados.

Ejercicio 4

Estrategia de Tiered Storage

Para retenciones de largo plazo (meses o años), el almacenamiento "hot" se vuelve costoso. Considera este enfoque en capas.

Comparativa de Capas

Capa Retención Tipo de almacenamiento Costo/GB
Hot 30 días Discos del broker Kafka $0.10
Cold 3 años S3 Glacier $0.0039

Cálculo para 3 años de retención

Naive (todo hot)
$26,280/mes
Tiered (hot + cold)
$1,060/mes
Ahorro del 96%

El enfoque en capas reduce el costo mensual de $26,280 a aproximadamente $1,060.

06
Síntesis

Lecciones Clave y Limpieza

Resumen de los aprendizajes y pasos para limpiar el entorno.

Lecciones Clave

1. Siempre verifica las configuraciones

Usa kafka-configs.sh --describe para comprobar la configuración actual antes de asumir.

2. Los cambios de retención son dinámicos

No se requiere reinicio ni hay pérdida de datos al modificar la retención.

3. El costo escala linealmente

Duplicar la retención duplica el costo de almacenamiento.

4. El tiered storage es esencial

Para retenciones largas, utiliza capas de almacenamiento frío para reducir costos drásticamente.

Limpieza

Salir del contenedor y detener el entorno:

exit
docker-compose down -v
